🪵 Workload Documentation Rules
Issue Tracking: Map every project requirement to a GitHub Issue.
Assignees: Assign yourself to an Issue before you start working on it. Never work on unassigned tasks.
Project Boards: Use a GitHub Project Board (Kanban style) with columns: To Do, In Progress, Review, and Done.
Commit Frequency: Commit code early and often. Large, single-day code dumps at the end of the semester look suspicious to automated plagiarism and contribution trackers.

🌿 Branching & Naming Conventions
NEVER CODE DIRECTLY ON THE MAIN BRANCH!! 
Use a feature-branch workflow with strict naming rules.

Branch Naming Nomenclature
Use lowercase letters, hyphens to separate words, and a category prefix:
  feature/ – For new features (e.g., feature/user-login, feature/database-setup)
  fix/ – For bug fixes (e.g., fix/auth-error, fix/broken-css)
  refactor/ – For code optimization without changing functionality (e.g., refactor/api-calls)


🔄 Pull Request (PR) & Code Review Workflow
Create a PR: When a feature is done, open a Pull Request from your branch into main.
Link Issues: Type Closes #IssueNumber in the PR description so the issue automatically shuts upon merging.
Peer Review: At least one other teammate must review the code, test it locally if needed, and click "Approve".
Conflict Resolution: The PR author is responsible for resolving any merge conflicts before merging.
The 24-Hour Rule: Give teammates at least 24 hours to review a PR before bumping them on chat.
